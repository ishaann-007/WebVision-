# Phase 2 Implementation Plan

## Scope and guardrails

This plan is based on independent checks of the local snapshot served over HTTP. Phase 2 changed documentation only. The HTML, CSS, JavaScript, image, and vendor files remain unchanged.

The implementation order is deliberately conservative: stabilize the local runtime first, then establish honest content fallbacks, then repair navigation and responsive/accessibility behaviour. No official PMAY data should be invented. The information architecture decision remains open until the functional baseline is stable.

## Proposed implementation order

1. Establish a local runtime mode and prevent optional/remote integrations from being startup dependencies.
2. Resolve the Bootstrap/X-editable compatibility path and eliminate uncaught local startup errors without editing vendor bundles.
3. Repair verified local asset paths and remove stale references.
4. Add local data-provider/fallback boundaries for API-dependent sections.
5. Repair navigation and explicitly classify external/unavailable services.
6. Fix responsive overflow after third-party and dynamic markup decisions are made.
7. Complete accessibility and regression checks across the three target viewports.

## Verified inventory and decisions

### Local content that is present

- The captured homepage shell, government/PMAY branding, navigation labels, hero/banner imagery, and static section headings are present in `PMAY (U).html`.
- The asset folder contains captured images, JavaScript, CSS, and vendor files, but filenames and references are not consistently aligned.
- The supplied snapshot includes captured third-party/error artefacts; these are not verified live content and must not be presented as such.

### Content that is not verified as locally available

- API-backed processes, beneficiaries, publications, partner data, Angikaar statistics/state data, and dynamic slider responses.
- Live translation, Google Custom Search results, Twitter timeline data, Facebook content, analytics, and other third-party runtime responses.
- Several referenced image files and most historical CSS/vendor-relative assets.

### Recommended treatment

- Use verified static snapshot content where provenance is clear.
- Use explicit unavailable states for backend or third-party features with no reliable local source.
- Retain valid external links only when the destination is known and the UI clearly indicates that it leaves the local site.
- Use demonstration data only for interaction mechanics, with an unmistakable demonstration label and no official-looking figures.

## Unresolved decisions before implementation

- Choose information-architecture Option A, B, or C in the roadmap before structural changes.
- Decide whether local search is required or whether search should remain an external link/unavailable state.
- Decide which third-party services, if any, are permitted to remain external in the hackathon demo.
- Confirm whether the captured Bootstrap/X-editable functionality is needed at all; removing unused editing/plugin code is lower risk than forcing incompatible versions.
- Approve the exact set of verified local content allowed to populate dynamic sections.

## Phase 3 exit checks

- Local HTTP reload produces no uncaught implementation errors.
- Required local assets resolve; remaining intentionally unavailable resources are documented.
- API-dependent sections do not make unsupported claims.
- Navigation and external-service status are explicit.
- `scrollWidth` equals `clientWidth` at all three target viewports.
- A repeatable smoke checklist records console, network, interaction, keyboard, and responsive results.
